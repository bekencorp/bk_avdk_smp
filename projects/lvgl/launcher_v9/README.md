# launcher_v9 Project Guide (480x480 RGB)

* [中文](./README_CN.md)

## 1. Overview

`launcher_v9` is an **application launcher (horizontal carousel home screen) + mini games** project for BK7259, built on **LVGL V9.3.0**. Every visual is drawn with native LVGL objects, with no image assets. It contains a 9-page carousel menu plus two playable games: 2048 and Juice Rush (fruit slicing). The UI is written in JavaScript (`ap/js/`) and executed at boot by the SDK `bk_jerryscript` component. An equivalent native C implementation is kept in the tree and can be selected with a single macro.

It is independent from the sibling `widgets_v9` (stock LVGL Widgets Demo) project. Both can be built and flashed separately:

| Project | Content | Build command |
| --- | --- | --- |
| `widgets_v9` | Stock LVGL Widgets Demo | `make bk7259 PROJECT=lvgl/widgets_v9` |
| `launcher_v9` | Carousel launcher + 2048 + Juice Rush | `make bk7259 PROJECT=lvgl/launcher_v9` |

Key points:

1. **Runnable application shell**: boots into the carousel home screen, tap the center card to open an app.
2. **Working RGB panel path**: RGB parallel panel, DPU, frame buffer, LVGL vendor layer and touch input.
3. **Reference template for new UIs**: add or remove cards in the `LC_APPS` table of `ap/js/launcher.js` to extend the menu.

## 2. Hardware And Display Parameters

| Item | Default |
| --- | --- |
| SoC | BK7259 |
| LVGL version | LVGL V9.3.0 |
| Panel interface | RGB parallel (24-bit pixel bus + SW SPI config bus) |
| Default panel driver | `st7701s_rgb_480x480` (`CONFIG_LCD_ST7701S=y`) |
| Default resolution | `480 x 480` |
| Pixel format | `ARGB8888` with DPU decompression |
| Render mode | `RENDER_PARTIAL_MODE` |
| Config SPI | CLK `GPIO_8` / CSX `GPIO_28` / SDA `GPIO_9` (bit-banged) |
| LCD reset | `GPIO_6` |
| Backlight | `GPIO_7` |
| Touch | `CONFIG_TP=y` |

> Wiring follows the SDK doc `ap/docs/bk7259/zh_CN/developer-guide/display/how_to_add_rgb_panel.rst` and `projects/multimedia/rgb_lcd_example`. If your panel model, resolution or GPIOs differ, adapt the display path first, then the UI.

**Touch pins must be confirmed on your board**: `CONFIG_TP_INT_PIN=6` collides with the LCD reset (`GPIO_6`). If your RGB board uses another touch INT pin, change it in `defconfig`, otherwise touch interrupts will not work.

## 4. What You See

After boot, `ap_main.c` initializes the RGB display path, then the UI backend builds the screens. By default the `bk_jerryscript` component runs the embedded bundle (entry `ap/js/main.js` calls `launcher_start()`), and the carousel home screen appears. Swipe left/right to switch cards, tap the center card to open an app.

| Module | Description |
| --- | --- |
| Carousel | Center snapping, title sync, page-dot sync |
| Card order | MUSIC / GALLERY / WEATHER / SETTINGS / CALENDAR / VOICE NOTE / WHATSAPP / 2048 / JUICE RUSH |
| 2048 | 4x4 board, four-way swipe merge, score/best, game-over page |
| Juice Rush | 60-second slicing with combos, bombs, slash and juice effects |
| Other cards | Show `THIS APP IS COMING SOON` at the bottom |

## 5. Quick Start

### 5.1 Prerequisites

1. You are in the SDK root: `bk_avdk_smp_release_4.0.1/`
2. The toolchain is configured.
3. The board has an ST7701S 480x480 RGB panel and a touch panel connected.

### 5.2 Build

```bash
make bk7259 PROJECT=lvgl/launcher_v9
```

Or through the CI wrapper:

```bash
./dbuild.sh make bk7259 PROJECT=lvgl/launcher_v9
```

The output goes to `build/bk7259/launcher_v9/`, independent from the `widgets_v9` build directory.

### 5.3 Flash And Run

Flash the firmware with the Beken tool, then power-cycle the board:

1. The serial log should show system boot, media service init and LVGL init.
2. Backlight (`GPIO_7`) is driven high.
3. The carousel home screen appears.
4. If touch matches your board, swiping and tapping work immediately.

## 6. Boot Flow

`ap/ap_main.c` is the entry point.

1. `main()` calls `bk_init()`.
2. `media_service_init()`.
3. `bk_frame_buffer_init()`.
4. Register the `launcher` CLI command.
5. `lvgl_app_launcher_init()` initializes display, touch and LVGL.

Inside `lvgl_app_launcher_init()`:

1. Look up the RGB panel descriptor: `bk_lcd_find_rgb_panel_by_name("st7701s_rgb_480x480")`.
2. Create the SW SPI config bus: `bk_display_spi_bus_new()` (CLK/CSX/SDA).
3. Create the RGB panel: `bk_lcd_rgb_panel_new()` (reset on `GPIO_6`).
4. Create the DPU controller: `bk_display_dpu_ctlr_new()`.
5. `bk_display_init()` and `bk_display_open()`.
6. Backlight on: `GPIO_7` high.
7. Fill `lv_vnd_config_t` (480x480, `RENDER_PARTIAL_MODE`, compressed output).
8. Compute the frame buffer size (480x480 bytes per buffer when compressed).
9. Allocate the LVGL frame buffers.
10. `lv_vendor_init()`.
11. `drv_tp_open()` when touch is enabled.
12. `lv_vendor_start()`.
13. Build the UI: with `LAUNCHER_UI_USE_JS=1`, `bk_js_init()` then `bk_js_eval("launcher.js", ...)` runs the embedded bundle (`js_bundle.c`); with `=0`, the C `launcher_start()` is called under the display lock.

JS runs in a dedicated `bk_jerryscript` task; the component holds the display mutex for the whole script/timer/event callback, so JS code never locks the display itself. Touch events are queued from the LVGL thread to the JS task, and the touch coordinates travel with each event.

On exit, `lvgl_app_launcher_deinit()` calls `bk_js_deinit()` first (the engine owns timers and event callbacks that reference LVGL objects), then stops LVGL. With the C backend it clears the cached pointers via `launcher_reset()`, `game_2048_reset()` and `juice_rush_reset()` after LVGL is gone, and finally releases frame buffers and display resources.

## 7. Configuration

### 7.1 Feature Switches

`ap/config/bk7259_ap/defconfig`:

| Option | Purpose |
| --- | --- |
| `CONFIG_LVGL=y` / `CONFIG_LVGL_V9=y` | Enable LVGL V9 |
| `CONFIG_BK_DISPLAY=y` | Enable the display framework |
| `CONFIG_LCD_RGB=y` | Enable RGB parallel panels |
| `CONFIG_LCD_ST7701S=y` | Enable the ST7701S 480x480 RGB driver |
| `CONFIG_DPU_DRIVER=y` | Enable the DPU controller |
| `CONFIG_FRAME_BUFFER=y` | Enable frame buffers |
| `CONFIG_TP=y` | Enable touch |
| `CONFIG_LVGL_FRAME_BUFFER_NUM=2` | Two LVGL frame buffers |
| `CONFIG_LVGL_TASK_STACK_SIZE=8192` | LVGL task stack |
| `CONFIG_PSRAM=y` | PSRAM enabled; the JS heap is served by `psram_malloc()` (`AP_PSRAM_HEAP`) |
| `CONFIG_PSRAM_AS_SYS_MEMORY` | Off: the system heap stays in SRAM, keeping LVGL memory behavior unchanged |
| `CONFIG_BK_JERRYSCRIPT=y` | Enable the bk_jerryscript (JerryScript) component |
| `CONFIG_BK_JERRYSCRIPT_HEAP_SIZE_KB=256` | JS heap size, allocated from PSRAM |
| `CONFIG_BK_JERRYSCRIPT_TASK_STACK_SIZE=32768` | JS task stack |
| `CONFIG_BK_JERRYSCRIPT_UI=y` | Enable the `lv.*` UI bindings |
| `CONFIG_BK_JERRYSCRIPT_AUTO_START` | Disabled: `ap_main.c` starts the engine explicitly |

> The RGB config bus uses bit-banged SPI, so `CONFIG_SPI` is not required.

### 7.2 Project-Level LVGL Config

`ap/lv_conf_custom.h` includes the SDK `lv_conf.h` first, then overrides:

| Option | Purpose |
| --- | --- |
| `LV_USE_DEMO_WIDGETS=0` | Widgets Demo disabled to save flash |
| `LV_FONT_MONTSERRAT_12/16/18/20/24/32/40/48=1` | All font sizes used by the UI |

Prefer this file over editing the shared LVGL component config.

### 7.3 ARGB8888 And Compressed Output

| Parameter | Default | Meaning |
| --- | --- | --- |
| `dpu_config.video.format` | `BK_PIXEL_FORMAT_ARGB8888` | DPU video layer format |
| `dpu_config.video.decompress` | `true` | DPU-side decompression |
| `lv_vnd_config.output_compress` | `true` | LVGL compressed output path |
| `draw_pixel_size` | `WIDTH * 64 * sizeof(bk_color_t)` | Draw buffer size in partial mode |
| `WIDTH` / `HEIGHT` | `480` / `480` | Must match the panel timing |

You normally do not need to touch these when only changing the UI.

### 7.4 480x480 Layout Constants

| Module | Values |
| --- | --- |
| Carousel card | 258x258, gap 26, container y=118 |
| Page dots | y=420, dot 10x10, slot 26 |
| Bottom panel | starts at y=436, height 44 |
| 2048 board | cell 80, gap 8, board 344x344 at (68, 64) |
| Juice Rush | fruit radius 34~44, gravity 900 px/s², HUD height 82 |

### 7.5 UI Backend Switch (JS / C)

Both implementations are compiled; one macro at the top of `ap/ap_main.c` selects the active one:

```c
#define LAUNCHER_UI_USE_JS 1   /* 1 = JavaScript, 0 = native C */
```

- `=1`: `bk_js_init()` + `bk_js_eval()` run `js_bundle.c`; the UI comes from `ap/js/`.
- `=0`: `launcher_start()` under the display lock; the UI comes from `ap/launcher.c`, `game_2048.c`, `juice_rush.c`.

Both look and behave the same. Change the macro and rebuild; no CMake edit is needed. The only cost is that the firmware carries both implementations, so flash usage is slightly higher.

### 7.6 JS Sources And Bundling

The JS pages live in `ap/js/` and are packed into a single C string array in `ap/js_bundle.c`, which is executed once at runtime by `bk_js_eval()`. Packing uses the shared converter shipped with the component, `ap/components/bk_jerryscript/tools/js2c.py`, so this project keeps no private copy. The merge order is fixed:

```text
ui_common.js → launcher.js → game_2048.js → juice_rush.js → main.js
```

After editing any `.js` file you must regenerate the bundle, otherwise the change never reaches the firmware. Run this from the project directory:

```bash
python3 ../../../ap/components/bk_jerryscript/tools/js2c.py \
    ap/js/ui_common.js ap/js/launcher.js ap/js/game_2048.js \
    ap/js/juice_rush.js ap/js/main.js \
    -o ap/js_bundle.c --header ap/js_bundle.h --name js_bundle
```

This is the **default** backend: the source is compiled into the firmware and does not depend on any filesystem. See 7.7 if you prefer loading it from a filesystem at runtime.

Both backends share the same JS engine heap: it goes through `psram_cache_malloc()`, which maps to `AP_PSRAM_CACHE_HEAP` in `partitions/bk7259/ram_regions.csv` (now 512KB / `0x080000`, enough for the 256KB heap plus context). That region is cacheable PSRAM, so CPU access stays close to on-chip SRAM speed.

### 7.7 Loading From The File System (Optional)

With `CONFIG_LAUNCHER_JS_FROM_FS` enabled, startup no longer runs `js_bundle.c`; instead the `launcher` application is read from the littlefs image mounted from the `usr_config` partition.

**Partition**: `usr_config` in `partitions/bk7259/auto_partitions.csv` has been enlarged to 1024K (offset `0x4C9000`).

**Build the image** (run from the project directory):

```bash
mkdir -p fs/launcher
cat ap/js/ui_common.js ap/js/launcher.js ap/js/game_2048.js \
    ap/js/juice_rush.js ap/js/main.js > fs/launcher/main.js

cat > fs/launcher/manifest.json <<'EOF'
{ "id": "launcher", "name": "Launcher", "version": "1.0.0", "entry": "main.js" }
EOF

../../../ap/components/littlefs/mkimg/mklittlefs \
    -c fs -b 4096 -p 256 -s 1048576 littlefs_js.bin
```

The image root must contain `launcher/` directly, without an extra `apps/` level (the mount point already is `/apps`). See [bk_jerryscript/README.md](../../../ap/components/bk_jerryscript/README.md) for the layout, manifest fields and tool parameters.

**Flash**: write `littlefs_js.bin` to `0x4C9000` (`usr_config`).

**Verify**: the boot log should show:

```text
ap0:js:I(xxx):mounted /apps on usr_config (0x4c9000, 1048576 bytes)
ap0:js:D(xxx):  launcher
ap0:js:I(xxx):js app 'launcher' running from fs
```

Notes:

- The image size must match the `usr_config` partition (1MB here), and the block/page parameters must match the littlefs adapter.
- After editing `ap/js/*.js`, just rebuild and reflash the image; **no firmware rebuild is needed**.
- A missing or corrupt image only logs a `file system not mounted` warning and does not block boot; the app start only fails when the backend is `y`.
- In filesystem mode both the script buffer and the `require()` copy live in PSRAM, so they do not consume the SRAM heap.

## 8. Common Modifications

### 8.1 Add Or Remove Cards

The card list lives in `ap/js/launcher.js` as `LC_APPS`; array order is display order:

```js
var LC_APPS = [
  { name: 'MUSIC', tag: 'PLAYER', top: 0x4B3BB0, bot: 0x171132, accent: 0xA897FF, kind: 1 },
  /* ... */
];
```

- `name` / `tag`: card title and category (Montserrat is ASCII-only).
- `top` / `bot`: card gradient.
- `accent`: index text, focus border and accent bar color.
- `kind`: icon branch used by `lc_icon_draw()`.

If you add a playable card, update `LC_APP_2048` / `LC_APP_GAME` index constants accordingly, then rerun the bundling command from section 7.6. With the C backend the same table is `s_apps[]` in `ap/launcher.c`.

### 8.2 Change Icons

All icons are composed from `shape()` / `ring()` inside `lc_icon_draw()` in `ap/js/launcher.js`.

**Do not use `transform_rotation/scale/skew`**: the software fill path ignores the matrix and instead goes through `refr_obj_matrix()`, which inflates the clip area by 1 px and can produce an out-of-range destination pointer. Compose rotated shapes from primitives instead (as done for the WhatsApp handset).

### 8.3 Change Panel Or Resolution

Update all of the following:

1. Panel name passed to `bk_lcd_find_rgb_panel_by_name()` in `ap/ap_main.c`.
2. `WIDTH` / `HEIGHT` macros in `ap/ap_main.c`.
3. The matching `CONFIG_LCD_xxx` switch in `ap/config/bk7259_ap/defconfig`.
4. Absolute-coordinate layouts of every page (see 7.4).
5. Font sizes in `lv_conf_custom.h` if needed.

### 8.4 Change Backlight And Reset GPIOs

| Function | Default | Location |
| --- | --- | --- |
| Backlight | `GPIO_7` | `bk_gpio_set_output_high(GPIO_7)` in `ap/ap_main.c` |
| LCD reset | `GPIO_6` | `panel_config.reset_pin` in `ap/ap_main.c` |
| Config SPI | `GPIO_8/28/9` | `rgb_cfg_bus` in `ap/ap_main.c` |
| TP reset/INT/I2C | `GPIO_5/6/1/0` | `ap/config/bk7259_ap/defconfig` |

## 9. Troubleshooting

### 9.1 Panel Not Found

1. Check `CONFIG_LCD_RGB=y` and `CONFIG_LCD_ST7701S=y`.
2. Make sure the name string matches the panel's `.name` exactly.
3. Make sure new sources are added to `ap/CMakeLists.txt`.

### 9.2 Black Screen

1. Panel name and resolution must match the real panel.
2. Check the RGB FPC, power rails and backlight.
3. Verify config SPI uses `GPIO_8/28/9`.
4. Verify `GPIO_6` is really the LCD reset pin.
5. Verify `GPIO_7` is really the backlight pin.

### 9.3 Touch Not Responding

1. `CONFIG_TP=y`.
2. `CONFIG_TP_RST_PIN`, `CONFIG_TP_INT_PIN`, `CONFIG_TP_I2C_SDA_PIN`, `CONFIG_TP_I2C_SCL_PIN` must match the board.
3. **`CONFIG_TP_INT_PIN=6` is currently shared with the LCD reset pin** — change it to the real touch INT pin.
4. The touch IC driver must be enabled and `drv_tp_open()` must run.

### 9.4 Random UI Failures Or Crashes

LVGL is not thread-safe. Any UI call outside the LVGL task must take the display lock:

```c
lv_vendor_disp_lock();
/* LVGL API calls */
lv_vendor_disp_unlock();
```

Increase `CONFIG_LVGL_TASK_STACK_SIZE` if the UI is heavy.

JS code does not need its own locking: the `bk_jerryscript` component holds the display mutex for the whole script/timer/event callback.

### 9.5 JS Init Failure Or Blank Screen

1. `js init failed: ...` or `context allocation failed` in the log: the JS heap could not be allocated. Check `CONFIG_PSRAM=y` and make sure `AP_PSRAM_HEAP` in `ram_regions.csv` is at least `CONFIG_BK_JERRYSCRIPT_HEAP_SIZE_KB` + 16KB; lowering the KB value also works.
2. `js app failed: ...`: script error. `bk_js_eval()` prints the reason and an approximate line.
3. Edited `ap/js/*.js` but the screen did not change: you forgot to rerun the bundling command from section 7.6.
4. Touch registers but pages do not switch: check that the event names match the binding table (`click`/`pressed`/`pressing`/`released`/`press_lost`/`scroll`) and that gesture code uses the coordinates from `lv.touch()`.
5. To confirm which backend is running, look for `js app running, bundle ... bytes` in the log.
